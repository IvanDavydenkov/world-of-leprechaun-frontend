# Design

## Context
Бэкенд поддерживает POST configs с count, DELETE configs/{id}, POST configs/bulk-delete с config_ids, DELETE configs и GET config-operations/{id}. Все изменения требуют Idempotency-Key и доверенный Origin, выполняются от текущего admin через users API. HTTP 202 означает только принятие.

## Goals / Non-Goals
Выдача и отзыв с честным отображением асинхронного результата. Не менять квоту, роль, профиль и не реализовывать повторную активацию отсутствующим HTTP-методом.

## Decisions
- Feature импортирует тип user из entities, не зависит от pages. Модальное окно открывается из строки каталога; на телефоне почти вся ширина экрана, кнопки от 44px.
- Zod проверяет count 1..20 и ответы операций; API работает только через generated RTK Query hooks. Доступ к внутреннему vpn-configs напрямую не используется.
- UUID создаётся на новое намерение. При сети/таймауте, partial/failed повторяется неизменённый payload с прежним ключом. Новые намерения блокируются до подтверждённого успеха или явной ошибки до принятия (400/403/404/409).
- Отзыв одного, выбранных (до 100) и всех требует подтверждения в окне; отсутствие списка не выдаётся за отсутствие конфигов. Возможен отзыв всех без знания списка, после явного подтверждения.
- GET статуса опрашивается каждые 2с до terminal или ошибки; повтор проверки доступен. Закрытие окна не отменяет backend-операцию, повторное открытие восстанавливает проверку в пределах текущей страницы. Перезагрузка страницы теряет локальное состояние; секреты и локальный persist не используются.
- Tags Users обновляют каталог после mutation и terminal status. Данные не изменяются оптимистически. На повтор mutation виджет статуса временно размонтируется, чтобы не остановить новый polling по старому partial.
- Proxy расширяется на /admin/users/…, сохраняя SPA /admin/users-list.

## Risks / Trade-offs
Реальные изменения VPN-хоста не выполняются при проверке: тесты используют синтетический API. Docker runtime отсутствует, конфигурация проверяется статически.
